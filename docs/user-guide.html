Open Distributed Services Engine

What, why, and how to use ODSE

A lab operator’s guide to discovering DPUs/IPUs, planning VM-to-VM forwarding, and collecting honest offload evidence — without treating planned commands as live hardware proof.

Dry-run: go Hardware --apply: gated Control point: labctl.py One DPU at a time

What

ODSE is an open toolkit for a hardware-accelerated, DPU/IPU-offloaded infrastructure path on Linux. It is the lab and automation layer for a vDSE-like outcome using open components: KVM/QEMU, SR-IOV, representor ports, OVS/OVS-DOCA where the vendor actually owns that path, and vendor-neutral OPI-style control where that is the vendor’s model.

For day-to-day use, ODSE is not “run Ansible and hope.” It is a staged lab workflow with one operator command:

python tools/labctl.py <domain> <stage> --config <file>

labctl hides vendor CLIs. You do not connect two lab VMs by typing ovs-vsctl, devlink, DAO, OPI, or tc by hand.

The first real use case

The implemented lab shape is deliberately small:

  • One server
  • One selected DPU/IPU
  • Two SR-IOV VFs
  • Two KVM/QEMU VMs (VF0 → VM1, VF1 → VM2)
  • Vendor-correct representors and forwarding (NVIDIA: on the DPU)
  • Guest traffic, then offload evidence, then cleanup of lab-owned objects

That is labctl vm2vm. Other domains exist because not every vendor is a VM-to-VM OVS story: Intel’s first-run path is network-function offload on the IPU; AMD is discovery-first until a forwarding control path is proven.

What “done” looks like for a run

Every stage writes JSON under tests/results/<vendor>/<run-id>/. A report generator turns that directory into one summary. Verdicts are conservative: unknown offload stays unknown. A planned SSH command with executed: false is not DPU proof.

Why

Why this project exists

VMware vDSE showed a useful model: move networking services off the host CPU onto a DPU, keep a consistent operator story across cards. That stack is proprietary. The open ecosystem already has the parts (SR-IOV, switchdev, OVS hardware offload, OVN, vDPA, OPI) but not one testable, vendor-honest assembly. ODSE exists so adopting offload does not require adopting a closed hypervisor.

Why one control point

If every operator improvises ovs-vsctl on the host, NVIDIA DPU-mode labs silently become ConnectX host-switchdev labs. If Intel is driven with NVIDIA representor names, the IPU path is fake. labctl plus ForwardingIntent force a single question: what did the operator ask for, and which backend actually owns forwarding?

Why dry-run is the default

Creating VFs, flipping eswitch mode, defining libvirt domains, and mutating DPU OVS are destructive. Three gates must all agree before a mutation runs:

  1. You passed --apply (and did not also pass --dry-run, which always wins).
  2. The YAML has safety.dry_run_default: false.
  3. The apply readiness gate passes (validated config, unchanged hash, management interface protected, vendor profile valid, prior stage outputs, a prior dry-run plan for that stage).

Example YAML keeps dry-run on. That is intentional. run-all-safe forces dry-run even if you pass --apply.

Why unknown stays unknown

Missing sysfs, empty SSH stdout, or “command not found” on a laptop is not evidence that IOMMU is off or that DOCA is missing. ODSE records null / UNKNOWN rather than inventing offloaded:yes or ready: false from absence. Hardware claims need inspected evidence.

Why vendors are not copied

NVIDIA DPU-mode OVS-DOCA is NVIDIA-specific. Marvell uses DAO/DPDK representors. Intel uses OPI and a DPU Operator. AMD starts at ionic discovery. Copying host OVS-TC onto those tracks would produce green demos and false certification.

How

Work top to bottom. Do not skip to --apply. First activities run on a laptop with no DPU. Advanced activities assume a filled lab file and a written change window.

Activity 0 · Setup

Prerequisites

  • Python 3.7 or later. The stdlib YAML fallback works if PyYAML is not installed.
  • This repository, commands run from the repo root.
  • Dry-run: no DPU, no ovs-vsctl, no libvirt required.
  • Later --apply: Linux host, one DPU/IPU, KVM/QEMU/libvirt, two guest images, and for NVIDIA DPU mode SSH to the BlueField Arm OS.
cd open-distributed-services-engine
python --version
Activity 1 · First commands

Confirm the toolkit is the control point

List backends, then print help. You should see three domains: vm2vm, intel-nf, amd-discovery.

python tools/vendorctl.py list-vendors
python tools/labctl.py --help
python tools/labctl.py vm2vm --help

Optional: run the no-hardware tests so you know the tree is healthy.

python -m unittest discover -s tests/unit
python -m unittest discover -s tests/vendor
python -m unittest discover -s tests/vendor-certification
If a test ever hangs on SSH to 192.0.2.10, that is a live probe leaking through dry-run. Stop it. Dry-run must record argv with executed: false.
Activity 2 · Readiness

Preflight and validate-config

Use the NVIDIA example. It is full of placeholders and is supposed to be dry-run only.

python tools/preflight_readiness.py --config config/lab-nvidia-vm2vm.example.yaml --markdown

python tools/labctl.py vm2vm validate-config --config config/lab-nvidia-vm2vm.example.yaml --json

Good preflight: READY_FOR_DRY_RUN_ONLY, empty blocking_issues, warnings about placeholders and VM images. Not “cleanup does not yet target DPU-side OVS” (that check is stale if you still see it — current cleanup plans DPU OVS for lab-owned objects).

Good validate-config: valid: true. DPU OVS validation is planned ssh … ovs-vsctl get/show on the DPU. You must not see a local host command ovs-vsctl --may-exist add-br br-int at this stage. Bridge create belongs to prepare-ovs, over DPU SSH.

Activity 3 · See the hardware story (read-only)

Discovery and capability report

On a laptop these probes mostly return “command not found.” That is fine. You are proving the pipeline, not inventing devices.

python tools/vendorctl.py discover --vendor nvidia-bluefield --json
python tools/capability_report.py --format markdown

python tools/labctl.py vm2vm discover --config config/lab-nvidia-vm2vm.example.yaml --json

On a real host, also:

python tools/inventory/dpu_inventory.py --pretty

Fill PCI and PF names from this output later. Do not copy <PF_PCI> from the example into a live file and call it inventory.

Activity 4 · Preview everything

Full dry-run pipeline

run-all-safe walks the VM-to-VM stages in order and always stays dry-run. It never runs cleanup.

python tools/labctl.py vm2vm run-all-safe --config config/lab-nvidia-vm2vm.example.yaml --dry-run --json

Then generate the cross-vendor go/no-go table:

python tools/vendor_readiness_matrix.py --configs config/*.yaml --output tests/results/vendor-readiness-matrix.md

Expect NVIDIA GO_FOR_HARDWARE_DRY_RUN, Intel/AMD discovery-oriented, Marvell blocked until DAO/DPDK. That matrix is not permission to --apply the example file.

Activity 5 · Learn the evidence layout

Read stage JSON and a report

Look under tests/results/nvidia-bluefield/<run-id>/. Typical files: run-metadata.json, validate-config.json, discover.json, representor-map.json, prepare-ovs.json, configure-forwarding.json.

For every command object, check:

  • dry_run: true and executed: false on this path
  • NVIDIA DPU mode: argv starts with ssh, not bare ovs-vsctl
  • Offload fields are null unless evidence was actually collected
python tools/report_generator.py --input-dir tests/results/nvidia-bluefield/<run-id>/ --output result-summary.md

On a dry-run laptop the verdict is often INCONCLUSIVE or functional-only. That is correct. Do not chase PASS_OFFLOAD_CONFIRMED from planned probes.

Activity 6 · Leave the example behind

Create a real lab YAML

Hardware work uses a copy. The copy is gitignored.

cp config/lab-nvidia-vm2vm.example.yaml config/lab-nvidia-vm2vm.yaml

Replace placeholders from discovery, not from documentation ranges:

FieldSource
host.name, host.management_interfaceThe host you will not break. Management iface is protected; never mutate it.
dpu.management_ip, dpu.ssh_user, dpu.ssh_key_pathReachability of BlueField Arm OS
dpu.pf_name, dpu.pf_pcidpu_inventory.py / vendorctl discover
VM image pathsPrepared guests; see docs/operations/vm-image-preparation.md

Keep safety.dry_run_default: true until you have a written change window. Re-run preflight on the filled file. Stay at READY_FOR_DRY_RUN_ONLY until you deliberately flip dry-run off and the apply gate can pass.

Never --apply against *.example.yaml. Never invent representor names (eth0v1 is not a BlueField VF representor; expect pf0vf0 / pf0vf1 from DPU devlink + portname).
Activity 7 · NVIDIA VM-to-VM (the main path)

Stage-by-stage, dry-run first

Default profile: nvidia-bluefield-dpu-mode.

Host owns

  • KVM / QEMU / libvirt
  • VF create on the PF (when SR-IOV is host-side)
  • VFIO passthrough into VMs
  • Guest lifecycle and guest SSH

DPU owns

  • Representors
  • OVS / OVS-DOCA
  • Forwarding / flows
  • Offload evidence (ovs-vsctl / dpctl on the DPU)

Use one --config. Omit --run-id to chain onto the latest run, or pin it to keep runs apart.

CFG=config/lab-nvidia-vm2vm.yaml

# Read-only
python tools/labctl.py vm2vm validate-config --config $CFG --json
python tools/labctl.py vm2vm discover --config $CFG --json

# Destructive stages: plan, inspect JSON, then --apply only if gates pass
python tools/labctl.py vm2vm prepare-host --config $CFG --dry-run --json
python tools/labctl.py vm2vm prepare-vfs --config $CFG --dry-run --json
python tools/labctl.py vm2vm prepare-switchdev --config $CFG --dry-run --json
python tools/labctl.py vm2vm discover-representors --config $CFG --json
python tools/labctl.py vm2vm prepare-ovs --config $CFG --dry-run --json
python tools/labctl.py vm2vm create-vms --config $CFG --dry-run --json
python tools/labctl.py vm2vm attach-vfs --config $CFG --dry-run --json
python tools/labctl.py vm2vm configure-forwarding --config $CFG --dry-run --json

When (and only when) preflight is ready, dry-run_default is false, and you have reviewed the plan for that stage:

python tools/labctl.py vm2vm prepare-vfs --config $CFG --apply --json
# …repeat --apply per destructive stage, never as a blind batch
python tools/labctl.py vm2vm configure-forwarding --config $CFG --apply --json
#StagePurposeDestructive?
1discoverInventory via backend + dpu_inventory.pyNo
2validate-configSchema + NVIDIA DPU-mode pinning + DPU OVS probes (plan)No
3prepare-hostTool presence; does not run ansible-playbookYes (packages, conceptually)
4prepare-vfsSR-IOV numvfs on the selected PFYes
5prepare-switchdevHost eswitch; skipped when DPU mode has host switchdev offYes
6discover-representorsMap VFs to DPU names such as pf0vf0No
7prepare-ovsDPU-side bridge (SSH). Refuses if DPU OVS or required DOCA is missingYes
8create-vmsLibvirt define from the VFIO templateYes
9attach-vfsVFIO attach VF PCI into each VMYes
10configure-forwardingSingle forwarding control point: intent → backendYes
11configure-vm-ipsGuest IPs on the VF under testGuest only
12run-trafficping / iperf3 between guestsNo
13validate-offloadDPU-side OVS/dpctl probes; offload_state stays unknown unless provenNo
14collect-evidenceSnapshots for the reportNo
15cleanupLab-owned DPU OVS + VMs; not in run-all-safeYes

configure-forwarding requires a prior discover-representors on the same run. Low-confidence names are refused when the profile requires high confidence. --force is invalid here.

If apply is blocked, read apply-readiness-gate.json / APPLY_BLOCKED_BY_READINESS_GATE. Typical causes: still on example placeholders, config hash changed after validate-config, no dry-run plan for that stage, missing DPU SSH fields, or --force on forwarding.

Activity 8 · Prove traffic, then leave the lab clean

Guest path, offload, report, cleanup

python tools/labctl.py vm2vm configure-vm-ips --config $CFG --json
python tools/labctl.py vm2vm run-traffic --config $CFG --json
python tools/labctl.py vm2vm validate-offload --config $CFG --json
python tools/labctl.py vm2vm collect-evidence --config $CFG --json
python tools/report_generator.py --input-dir tests/results/nvidia-bluefield/<run-id>/

python tools/labctl.py vm2vm cleanup --config $CFG --dry-run --json
python tools/labctl.py vm2vm cleanup --config $CFG --apply --json

Guest SSH uses vms[].management_ip or virsh domifaddr, never the VF test address. Cleanup deletes DPU OVS objects this run marked lab-owned. Unknown bridges return UNKNOWN_BRIDGE_REFUSED. --force may skip the dry-run-plan check for cleanup only.

Activity 9 · Other vendors

Do not start these with NVIDIA OVS

Intel IPU — network function, not VM-to-VM

python tools/labctl.py intel-nf validate-config --config config/lab-intel-network-function-offload.example.yaml --json
python tools/labctl.py intel-nf discover --config config/lab-intel-network-function-offload.example.yaml --json
python tools/labctl.py intel-nf validate-opi --config config/lab-intel-network-function-offload.example.yaml --json
python tools/labctl.py intel-nf validate-dpu-operator --config config/lab-intel-network-function-offload.example.yaml --json
python tools/labctl.py intel-nf deploy-network-function-dry-run --config config/lab-intel-network-function-offload.example.yaml --json

Stages continue with deploy-network-function (still dry-run unless apply gates pass), placeholder run-traffic, collect-evidence, cleanup. Missing OPI or operator → OPI_ENDPOINT_REQUIRED / DPU_OPERATOR_REQUIRED. Placement must be ipu.

Intel labctl vm2vm remains discovery-required for representor/OVS VM-to-VM. Do not assume BlueField semantics.

AMD Pensando — discovery first

python tools/preflight_readiness.py --config config/lab-amd-vm2vm.example.yaml --json
python tools/labctl.py amd-discovery validate-config --config config/lab-amd-vm2vm.example.yaml --json
python tools/labctl.py amd-discovery discover-device --config config/lab-amd-vm2vm.example.yaml --json
python tools/labctl.py amd-discovery discover-ionic --config config/lab-amd-vm2vm.example.yaml --json
python tools/labctl.py amd-discovery discover-rdma --config config/lab-amd-vm2vm.example.yaml --json
python tools/labctl.py amd-discovery discover-sriov --config config/lab-amd-vm2vm.example.yaml --json
python tools/labctl.py amd-discovery dry-run-create-vfs --config config/lab-amd-vm2vm.example.yaml --json
python tools/labctl.py amd-discovery discover-representors --config config/lab-amd-vm2vm.example.yaml --json
python tools/labctl.py amd-discovery discover-switchdev --config config/lab-amd-vm2vm.example.yaml --json
python tools/labctl.py amd-discovery discover-ovs-feasibility --config config/lab-amd-vm2vm.example.yaml --json

ionic stats are not offload proof. Representors/switchdev/OVS stay undiscovered until observed. Do not set allow_assumed_forwarding: true.

Marvell OCTEON — DAO/DPDK gate

python tools/preflight_readiness.py --config config/lab-marvell-vm2vm.example.yaml --json

Until DAO, DPDK, hugepages, and a representor source exist, the track is BLOCKED_MISSING_VENDOR_RUNTIME / MARVELL_DAO_MISSING. Host OVS forwarding is refused. Mapping model is DPDK, not NVIDIA portname.

Activity 10 · Advanced

After the first successful dry-run path

Pin a run id

Use --run-id to resume a specific directory or to compare before/after. Default reuses tests/results/<vendor>/.latest.

python tools/labctl.py vm2vm discover --config $CFG --run-id lab-2026-08-16 --json

Inspect forwarding intent without calling the backend

python tools/forwarding_intent.py --config $CFG --json

NVIDIA DPU-mode intent uses datapath doca when the YAML says OVS-DOCA. A generic system datapath is only for configs that request it (or the advanced host-switchdev profile).

NVIDIA host-switchdev (not the default)

Profile nvidia-connectx-host-switchdev puts OVS on the host. Select it explicitly (nvidia.mode: host-switchdev, ovs_location: host, allow_host_ovs_for_forwarding: true). First-run VM-to-VM must not use this. Mixing it with DPU-mode YAML fails validate-config.

Verbose plans

python tools/labctl.py vm2vm prepare-ovs --config $CFG --dry-run --json -v

Stderr logs planned argv with secrets redacted. Confirm SSH to the DPU, not local add-br.

Direct tools (debugging only)

Prefer labctl. These exist for inspection:

python tools/topology-discovery/vf_to_representor_map.py --location dpu --config $CFG --json
python tools/offload-checker/ovs_offload_checker.py --help
python tools/lab_cleanup.py --config $CFG --dry-run

Apply readiness gate failures

Fix the named check; re-run validate-config and a dry-run of the same stage; then --apply. Do not disable safety.require_apply or forbid_management_interface_changes — the loader rejects that.

Reports and verdicts

Possible finals include PASS_FUNCTIONAL_ONLY, PASS_OFFLOAD_PROBABLE, PASS_OFFLOAD_CONFIRMED, FAIL_CONNECTIVITY, FAIL_SETUP, INCONCLUSIVE. Confirmed offload needs DPU-side evidence, not host hw-offload=true alone.

L2 segment (three VMs)

Modeled as forwarding.type: l2-segment in the intent schema. The current lab YAML is hard-limited to two VMs / two VFs. Do not pretend a 3-VM fabric is executable yet.

Adding a backend or running CI locally

Implement VendorBackend under plugins/<name>/, register it, add fixtures and vendor tests, keep unknown as null. See the README “Add a new backend” section and docs/operations/vendor-implementation-roadmap.md.

Safety rules

  • One DPU/IPU at a time.
  • Dry-run first. --dry-run wins over --apply.
  • Never change host.management_interface.
  • --force is cleanup-only, never forwarding/OVS setup.
  • Do not enable host OVS forwarding in NVIDIA DPU mode.
  • Do not delete an OVS bridge unless this run marked it lab-owned.
  • Do not claim offloaded:yes from planned commands or host OVS in DPU mode.
  • Do not copy NVIDIA OVS-DOCA, host switchdev, or pf0vfN naming onto Intel, AMD, or Marvell.
