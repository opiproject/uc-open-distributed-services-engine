2. Test failures that must be fixed
P0-1: ForwardingIntent datapath mismatch

Failing test:

tests/unit/test_forwarding_intent.py::BuildForwardingIntentTests::test_intent_carries_bridge_and_datapath_details


Observed:

Expected: datapath_type == system
Actual:   datapath_type == doca


This likely means the test still assumes a generic/host OVS datapath, while the final NVIDIA default profile now uses DPU-side OVS-DOCA / doca datapath. This is probably a test fixture drift, not necessarily a product bug, but it must be resolved.2.txt

Fix direction

Either:

Option A:
  Update the test fixture to expect doca for the NVIDIA DPU-mode config.

Option B:
  Split generic ForwardingIntent tests from NVIDIA-specific DPU-mode tests.


My recommendation: Option B. Keep one generic fixture expecting system, and a separate NVIDIA DPU-mode fixture expecting doca.

P0-2: IOMMU readiness semantics are wrong or test is stale

Failing test:

tests/unit/test_vf_assignment_plan.py::VfAssignmentPlanTests::test_iommu_from_samples_does_not_invent_ready


Observed:

Expected: ready is None
Actual:   ready is False


This matters. If sysfs is absent in a test/container environment, that is unknown, not proof of “not ready.” For a safety-first hardware framework, unknown should remain None or UNKNOWN, not False, unless the code has actual host evidence.2.txt

Fix direction

I recommend restoring the safer contract:

ready = None
status = "UNKNOWN"


when the sysfs root or IOMMU evidence cannot be inspected.

P0-3: NVIDIA configure-forwarding test still sees host path

Failing test:

tests/vendor/nvidia/test_configure_forwarding.py::NvidiaConfigureForwardingTests::test_two_endpoint_bridge_forwarding_is_planned


Observed:

Expected: NVIDIA BlueField/ConnectX E-Switch
Actual:   NVIDIA BlueField/ConnectX E-Switch (host path)


This is the most important failure because it touches the ambiguity we spent time removing. For the default NVIDIA profile, the path must be:

nvidia-bluefield-dpu-mode
OVS/OVS-DOCA on DPU
representors on DPU
host OVS forwarding disabled


The test result shows at least one test/backend path is still defaulting or falling into the host path.2.txt

Fix direction

Update the NVIDIA backend/test fixture so default configure-forwarding uses:

control_entity:
  labctl -> nvidia backend -> DPU-side OVS/OVS-DOCA -> BlueField E-Switch

forwarding_entity:
  NVIDIA BlueField/ConnectX E-Switch


If host path is needed, it should only appear under:

nvidia-connectx-host-switchdev

4. labctl validate-config audit

I ran:

python tools/labctl.py vm2vm validate-config --config config/lab-nvidia-vm2vm.example.yaml --json


It completed successfully and produced a DPU-side OVS validation plan using remote SSH dry-run commands. That is aligned with the desired NVIDIA DPU-mode model. The output is here: labctl validate-config output, and the associated log is here: labctl validate-config log.

Concern

The log also shows local OVS bridge planning commands:

ovs-vsctl --may-exist add-br br-int
ovs-vsctl set bridge br-int datapath_type=doca


This is concerning in NVIDIA DPU mode. In that profile, host OVS should not be the forwarding owner. The DPU-side OVS/OVS-DOCA should own bridge/representor forwarding.

This needs inspection

There are two possibilities:

Benign:
  These local commands are generic dry-run artifacts but not used in the NVIDIA DPU-mode path.

Bug:
  prepare-ovs/configure-forwarding still plans host-side OVS changes even when nvidia.mode == dpu.


Until this is confirmed, I would not run --apply.
